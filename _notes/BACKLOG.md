### 2. 演出請假（原構想為 RSVP，2026-08-03 改定）

**原構想（RSVP，已否決）**：演出/排練建立後，系統主動問團員「是否參加」、要團員主動回覆。
2026-08-03 討論後否決——團員預設就是「要參加演出才會來排練」，本來都會來，不需要一個一個
主動確認；且排練層已是「預設出席＋請假」，再疊一套主動 RSVP 只會與請假打架、讓團員混淆。

**真正的需求 → 演出請假（採用）**：團員可能臨時有大事/出事無法出席演出，需要能請假。
現況是個缺口——**只有排練有請假**（`LeaveRequest`，綁 `Rehearsal`），**演出層沒有請假機制**。

**定案（2026-08-03）**：做「演出請假」，**需幹部審核**，比照現有排練請假流程：

```
團員在演出詳情頁點「這場演出請假」→ 填原因送出
        ↓
幹部審核（核准／拒絕）
        ↓
核准 → 該場演出標記為請假（記在 PerformanceAttendance）
```

首頁的待審／審核結果通知也比照現有排練請假（見 §4.11）。

**現況參考**：`PerformanceAttendance`（`event` + `member` + `confirmed`=是否到場 + `checked_in_at`，
unique(event, member)）目前只有 Admin、無前端；`confirmed` 是「事後到場」語意，與「事前請假意願」不同。

**實作方向（待實作時再定細節）**：
- model 掛法比照 `LeaveRequest`，但避免「rehearsal / event 二選一互斥」那種坑
  （才剛在槍手案淘汰 `PartAssignment` 的 member/guest 互斥，不宜再引入）。
  候選：擴充 `PerformanceAttendance` 承載請假狀態＋原因＋審核欄位，或另建演出請假記錄。
- 核准後如何標記出席狀態、與 `confirmed`（到場）如何並存，實作時一併定。

### 5. 槍手／外援（客座團員）身分與前端管理

**現況**：`GuestMember` model（`apps/events/models.py`）綁定單一演出（`event` 必填 FK、CASCADE），
只能透過 Django Admin 操作、無前端；被 `PartAssignment.guest_member`（CASCADE）參照。

**2026-07-31 討論結論 —— 改採「槍手是一種身分」（方案 C）**
不另開槍手表，改把槍手併入 `User`（人員表），用身分區分「正式團員 / 槍手」。
原因：現況「一個槍手綁一場」撐不住兩個需求——
- 槍手可能連續參加好幾場（現況要每場重建，系統不認得是同一人）
- 槍手日後可能轉正為正式團員（現況轉正後，過去以槍手身分的履歷不會跟著走）

方案 C 下：槍手一人一筆、參加哪些場由分譜分配帶出；轉正只需改身分，履歷天然延續。

**先前考慮並放棄的方向（方案 A／B）**
> 註：A／B 當時未逐條記錄，以下依「方向從補前端轉為身分制」的討論主軸事後補述，供理解 C 為何勝出。
三案的分水嶺是：A／B 都還把「槍手當成一張獨立的表」，只有 C 把槍手升格為「人員表（`User`）裡的一種身分」。

| 方案 | 做法 | 為何放棄 |
|------|------|---------|
| A（補前端）| 保留現況 `GuestMember`（一個槍手綁一場），只補前端頁面讓幹部不必進 Admin | 沒解決根本問題：跨場仍要每場重建、系統不認得同一人；轉正履歷接不上 |
| B（改良槍手表）| 仍是獨立槍手表，但改成可跨場（`event` 改選填或多對多）| 轉正時履歷斷在兩張表之間；且要長期維護「槍手表 + `User`」兩套人員資料與查詢 |
| **C（身分制，採用）**| 淘汰 `GuestMember`，槍手併入 `User`，用身分欄位區分正式／槍手 | — 跨場靠分譜分配帶出、轉正只改身分，履歷天然延續 |

**支撐可行性的前置事實（已於 2026-07-31 查核）**
- 目前資料庫無任何 `GuestMember` 資料、無 `PartAssignment` 用到 guest → 可直接淘汰，不需搬遷
- 登入用「帳號（username）」非 email → email 可放寬為可空（槍手常沒 email）
- `GuestMember` / `PartAssignment` 皆無前端（只在 Admin）→ 淘汰不影響任何畫面

**方案 C 會牽動的改動（概要，實作前再細化）**
- `User`：新增「槍手」身分、`email` 改為可空、新增「來自樂團」欄位；建槍手時不寄帳密信、不給可用密碼
- 移除 `GuestMember`、移除 `PartAssignment.guest_member`（分譜分配改只用 `member` 指 User）
- 通訊錄與通訊錄名冊報表要把槍手分流（正式名冊不含槍手）

**登入層級決策（2026-08-02 定案）—— 採 (a) 純名冊型起步**
三個層級曾並列考慮：
- **(a) 純名冊型**：槍手不登入，只是幹部登記的「人」，出現在分譜分配 / 演出名單 / 出席；本人不碰系統。最單純，且「跨場 + 轉正」仍成立（轉正時才開帳號）。**← 採用**
- (b) 輕度自助型：槍手能登入，只做與「來幫忙演出」直接相關的事。
- (c) 等同團員型：槍手登入後幾乎與正式團員相同，只差身分標記。**排除**——外部人登入後幾乎等同團員，最大化團員限定資料曝光，與下表 ❌ 自相矛盾。

選 (a) 的理由：(a) 已滿足方案 C 的兩個核心目標（跨場 + 轉正），登入能力對這兩件事無貢獻；槍手是信任較低的外部人，不給登入＝沒有 session＝團員限定資料沒有可外洩的路徑。**(a) 是 (b) 的嚴格子集**，資料模型完全一樣，日後真出現「槍手要自助抓分譜」的痛，再對個別槍手開通即可，模型不動。

#### 方案 C 實作藍圖（(a) 純名冊型）

**核心概念**：槍手 = 一筆 `User`、有帳號雛形但**無法登入**；參加哪些場完全由既有 `PartAssignment` / `PerformanceAttendance` 反向帶出，人身上不記「綁哪一場」。

```
現況（要淘汰）                          方案 C（身分制）
GuestMember ──event(必填)──▶ 一場        User(role=guest) ──被多場參照──▶ 多場
     ▲ CASCADE                              ▲ PartAssignment.member
換一場就重建、系統不認得同一人              同一人天然跨場、轉正只改 role
```

**（1）資料模型改動**

`User`（accounts）：
| 改動 | 內容 | 說明 |
|------|------|------|
| `Role` 新增 `GUEST` | `GUEST = 'guest', '槍手'` | 沿用既有 role 機制，`is_officer` 自然為 False，不新增布林欄位 |
| `email` 放寬 | `null=True, blank=True`（保留 `unique`）| 槍手常無 email；Postgres 允許多個 NULL 不衝突 |
| 新增 `from_band` | `CharField('來自樂團', max_length=100, blank=True)` | 承接 `GuestMember.from_band` |
| `REQUIRED_FIELDS` | 移除 `email`，留 `name` | email 不再強制 |

`PartAssignment`（events）：移除 `guest_member` FK；`member` 改 `null=False`；`clean()` 的 member/guest 互斥驗證整段刪除（同時清掉附錄四那條「互斥驗證可被 ORM 繞過」的技術債）。

移除 `GuestMember` model：DB 已查核無資料、無 PartAssignment 參照 → 直接 drop table，**不需搬遷**。

> **樂器欄位落差**：`User.instrument` 指 `InstrumentFamily`（族群，粗），舊 `GuestMember.instrument` 指 `InstrumentType`（樂器，細）。方案 C 下槍手比照團員存族群即可——每場精確樂器本來就記在 `PartAssignment.instrument`（InstrumentType），不遺失資訊。

Migration 順序：① accounts（Role 加 GUEST 僅 choices + 新增 from_band + email 改 null/blank）② events（PartAssignment 移除 guest_member、member 改 null=False；刪除 GuestMember）。

**（2）系統流程**

```
新增槍手：幹部填表(姓名必填/來自樂團/樂器族群/聲部/電話/email 選填)
  → user = User(role=GUEST, is_active=True, must_change_password=False)
    user.set_unusable_password()   # 關鍵：登不進系統；不寄帳密信
  → 槍手進入人員池，立即可在分譜分配下拉被選取

指派演出：分譜分配 member 下拉 = 正式團員 + 槍手
  → 同一槍手可被多場 PartAssignment 參照 → 天然跨場、系統認得同一人

轉正：幹部按「轉為正式團員」
  → role: guest → member；補 email；must_change_password=True + 給臨時密碼
    （直接複用現有「幹部代建帳號」流程）
  → 過去所有 PartAssignment / PerformanceAttendance 仍指向同一 User pk
    ∴ 履歷零搬遷、天然接上
```

額外好處：槍手成為 `User` 後，`PerformanceAttendance.member`（現況只吃 User）**也能記錄槍手演出出席**——現況 GuestMember 做不到。

**（3）資安守則（硬性規定，2026-08-02 資安盤點結論）**

背景：系統登入只有「帳號＋密碼」一條路（`ModelBackend`，無自訂後端、無 password reset、無 LINE/OAuth 登入），`set_unusable_password()` 的槍手在認證層即被擋。真正的風險面是「member-tier 頁面只擋 `@login_required`、不看身分」——槍手一旦有 session 就能踩到全庫樂譜、團員限定公告、通訊錄含電話等（§1660 表中 ❌ 項）。故：

1. **建立槍手鐵則**：一律 `set_unusable_password()` + 不寄帳密信 + `must_change_password=False`。
2. **顯式拒絕 guest 登入（採用）**：在 `AuthenticationForm.confirm_login_allowed()` 加 `if user.role == User.Role.GUEST: raise ValidationError('此帳號不可登入。')`。把「槍手不可登入」變成顯式、不因未來新增功能（如 password reset）而破的規則，不依賴「剛好沒有 reset」這種隱性前提。走 (b) 時再對被開通的槍手放行。
3. **查詢分流是資安邊界，非顯示問題**——下列既有查詢不改就會讓槍手滲進團員視圖：
   | 位置 | 現況 | 必改 |
   |------|------|------|
   | `member_directory` accounts/views.py:160 | `.exclude(role=ADMIN)` | 加 `.exclude(role=GUEST)`（含電話通訊錄不可含槍手）|
   | `member_directory_report` accounts/views.py:206 | 同上 | 加 `.exclude(role=GUEST)` |
   | `attendance_report` events/views.py:405 | `.filter(is_active=True).exclude(role=ADMIN)` | 依語意決定是否排除 GUEST（排練出席 matrix 是否含槍手）|
4. **`is_active` 取捨**：槍手保持 `is_active=True`（`attendance_report`／分譜下拉用 `is_active=True` 撈人，False 會使槍手無法被指派）。登入安全由第 2 點保證，不靠 `is_active=False`。
5. **根本原則（列為 (b) 前置條件）**：關鍵資源（全庫樂譜、團員通訊錄、團員限定公告）從「只 `@login_required`」升級為明文白名單 `role in (MEMBER, OFFICER, ADMIN)`，令未來任何新身分**預設拿不到**。改動面較大，(a) 階段可不做，但 (b) 開放登入前必做。

### 9. 會費系統重構：期別主檔 ＋ 團員自助申報 ＋ 自動入帳（S1–S4 已完成，2026-08-06）

2026-08-04 與幹部討論定案，2026-08-06 依分階段 S1–S4 全數實作完成。以下保留當初的實作藍圖與各階段設計，
作為此系統的完整設計說明；實際落地細節（migration、view）見各階段「實作重點」與 §4.7。

#### 背景與現況缺口

現況（見 §4.7）：`FinanceRecord`（收支明細）與 `MembershipFee`（會費）是同一 app 的兩個獨立 model，
**互不相通**——幹部在會費頁勾「已繳」不會產生任何收入，會費報表也只算人數、不算金額，
所以「財務總收入」根本不含會費。且會費期別是自由文字、金額每列各自填，缺乏單一來源。

定案的目標：① 會費金額由「期別」統一決定；② 團員能自助申報繳費（現金／轉帳）、幹部確認；
③ 確認繳費自動入帳到收支明細，「當年度收支」按實際收款日彙總；④ 會費管理移進「財務」，報表只留列印。

#### 資料模型

**新增 `FeePeriod`（會費期別主檔，band_finance／finance app）**

| 欄位 | 說明 |
|------|------|
| year | 年份（供報表分組；收入年度另按收款日，不靠這個）|
| term | 上期／下期（或期別名稱）|
| amount | 該期固定團費（全團同一金額，團員不可改）|
| start_date / end_date | 繳費起訖日（時段不定，幹部/管理員可調整）|
| created_by | 建立者（關聯 User）|

- 幹部/管理員 CRUD 期別；建立後，**每位在團團員對這期天然就是「應繳未繳」**。
- **不預建** per-member 列：報表用「在團團員 × 這期」join，沒有繳費列的人＝應繳未繳
  （沿用現有 `membership_fee_report` 的寫法，團員入退團自然處理）。

**改造 `MembershipFee`（每人對某期的繳納狀態）**

| 欄位 | 變更 | 說明 |
|------|------|------|
| period | 改為 FK → `FeePeriod` | 取代原本的自由文字期別 |
| amount | 保留 | **繳費當下自 FeePeriod 快照**，之後改期別金額不竄改歷史 |
| status | 新增 | `reported`（團員申報待確認）/ `paid`（已確認）/ `void`（作廢）；無列＝應繳未繳 |
| payment_method | 新增 | `cash`（現金）/ `transfer`（轉帳掃碼）|
| collected_by | 保留 | 現金：團員選的收款幹部 |
| account_last5 | 新增 | 轉帳：匯款帳號末五碼，供財務對帳；**幹部限定可見、確認後可清除** |
| paid_at | 保留 | 幹部確認繳費日＝實際收款日（收入認列基準）|
| finance_record | 新增 FK → `FinanceRecord`（SET_NULL）| 確認時自動產生的那筆收入，供作廢/退回時連動 |

> 一期一次仍靠 `unique(member, period)`。修正打錯字一律**用編輯**（一期一列）；真要移除由管理員硬刪。

#### 狀態流（申報 → 確認，與請假審核同構）

```
幹部/管理員建立 FeePeriod（年份+期、金額、繳費起訖日）
        ↓  每位在團團員 = 應繳未繳
團員自助申報（擇一）
  ├─ 現金：選收款幹部 → status=reported, payment_method=cash, collected_by=該幹部
  └─ 轉帳：頁面顯示樂團帳戶固定 QRCode，填匯款末五碼 → status=reported, method=transfer, account_last5
        ↓
幹部確認繳費（現金：收款幹部；轉帳：財務幹部拿末五碼+金額對帳單）
  → status=paid, paid_at=今天, amount 自 FeePeriod 快照
  → 自動建立一筆 FinanceRecord（type=收入, category=會費, date=paid_at, amount）
     並記於 MembershipFee.finance_record
        ↓
（幹部代登記：沿用現有 fee_edit，可略過申報直接建 paid — 保留彈性）
```

首頁通知比照請假：團員可看自己申報的確認結果、幹部可看「待確認會費」筆數（實作時定）。

#### 刪除層級（比照專案既有「管理員限定硬刪」慣例）

| 角色 | 權限 |
|------|------|
| 團員 | 自己的申報在 `reported`（待確認）時可撤回；一旦 `paid` 不可刪 |
| 幹部 | 標記**作廢**（`status=void`，軟刪、留痕）；不可硬刪 |
| 管理員 | 可**硬刪**（`member.delete()` 級，比照 `leave_delete`／`event_delete`）；作廢的那筆連動的 FinanceRecord 一併處理 |

#### 收入認列：現金收付制（解決「期數與年度對不上」）

**會費收入以實際收款日（`paid_at`）認列，與期別的年份脫鉤。**

- 確認繳費自動產生的 FinanceRecord，`date = paid_at`。
- 「當年度收支」＝**按 FinanceRecord 日期篩年份**，不看期別叫什麼、跨不跨年。
- 例：「2026 上半年」會費拖到 2027/1 才繳 → 算 **2027** 年收入（錢那年才進來）。
- 作廢/退回 `paid` 紀錄時，連動作廢/刪除 `finance_record`，避免帳面殘留。
- （不採權責發生制：對社團偏複雜，也不符「一年統整實收多少」的直覺。）

> 修正先前 §「會費 vs 財務」的說法：當年度收支**不需要**期別結構化年份，因為按收款日算；
> `FeePeriod.year` 只給「會費繳納情況」報表分組用。

#### Nav 與報表調整

- **財務**改成下拉：`收支明細`（現有）＋ `會費期別/繳納`（新）——管理入口集中在財務。
- **報表**下拉：新增可列印的 `當年度收支`（按年份彙總收支明細）；`會費繳納情況` 維持可列印。

### 10. 部署 Web 供幹部測試 — P0 待討論

2026-08-09 記錄。目前系統只跑在本機開發環境，其他幹部無法實際連線試用。需要一個能讓幹部點來點去測試的部署，實作前待討論：

- **目標**：先求「幹部連得到、能操作試用」即可，不必一步到位做正式上線（正式部署另見 [SETUP.md](SETUP.md) 情境 D 與 Architecture 八、伺服器規劃）。
- **待決定**：放哪（自架 vs 雲端 PaaS）、連線方式/網域、用測試資料還是真資料、`.env` 機密值怎麼帶上去（見 SETUP.md 情境 C/D）、`DJANGO_DEBUG` 與 `DJANGO_ALLOWED_HOSTS` 設定。
- **範圍拿捏**：測試性質的部署可簡化（單機、不接真 LINE/Email），與未來正式環境分開規劃；但 `DEBUG=False` 等安全設定仍建議比照，避免測試站外洩。

**討論走向（2026-08-09，未定案）**：兩條候選路線，因手邊有閒置舊電腦，目前傾向先 A 之後再 B。

**候選路線 A — 雲端 PaaS（零維運，但會休眠）**

- **Render**（app 免費、閒置休眠、首次請求約 1 分鐘喚醒——測試可接受）＋ **Neon 或 Supabase**（永久免費 Postgres；不用 Render 自家 30 天會過期的免費 DB）。
- **媒體（分譜/QR）**：Render 免費磁碟為臨時性、重部署會清空 → 要持久接 **Cloudflare R2 私有 bucket**（S3 相容、`django-storages`，維持 §4.19 分譜下載權限）；或先接受重傳、延後決策。
- **三大雲（AWS/GCP/Azure）已評估後排除**：對此情境過度工程、免費多為限時或需信用卡、有意外帳單風險（如 AWS 免費 12 個月後轉收費）。真正永久免費又常駐的雲端只有 Oracle Cloud Always Free，但那是自管 VM（≈ 路線 B 工作量）。

**候選路線 B — 家機自架（常駐免費，可與 NAS 合併）← 目前傾向**

- **背景**：手邊兩台閒置電腦，一台太舊擬淘汰、一台裝 Windows；擬用留下的那台。
- **常駐免費**：自架不休眠、永久 $0（僅電費），且是 Architecture 八「汰換電腦當伺服器」的種子，測試站可長成正式站。
- **NAS ＋ Web 同機但隔離**：對上 Architecture 八「Docker 將 NAS 與 Web Server 分開」。做法用 **Proxmox**（裸機 hypervisor：NAS VM ＋ Ubuntu Web VM，最貼使用者的 VM 經驗）或 **TrueNAS SCALE**（NAS OS ＋ Django 跑 Docker 容器）；避免把對外 Web 與 NAS 資料混在同一 OS（資安/穩定）。維持 Windows 亦可（SMB 分享 ＋ Waitress/WSL2）但隔離最弱。
- **對外曝露免固定 IP**：用 **Cloudflare Tunnel** 或 **Tailscale**——機器主動建連、不需固定 IP/開 port/曝家裡 IP，HTTPS 由通道端處理。Tailscale 私有（幹部裝 App、最安全、不上公網）或 Tailscale Funnel／Cloudflare Tunnel（開網址即連）。
- **Windows 注意**：`gunicorn` 為 Unix-only、Windows 不能原生跑 → 用 **Waitress**（Windows 原生 WSGI）或 **WSL2/VM/Docker** 跑標準 Ubuntu＋gunicorn 堆疊（後者較貼合正式環境）。
- **與當年 VM+Tomcat 的差異**（供對照）：Tomcat→gunicorn/WSGI；SSL 改免費自動（Let's Encrypt/Caddy/Cloudflare）；固定 IP 不再必要（Tunnel 取代開 port）。

**共通事項（不論 A/B）**：

- **資料**：用**假資料**（fixtures ＋ 少量假團員/幹部帳號），避免真團員個資上測試站。
- **部署缺件**：`requirements.txt` 補 WSGI 伺服器（Linux 用 `gunicorn`、Windows 用 `waitress`）＋ `whitenoise`；`.env` 設新 `SECRET_KEY`、`DEBUG=False`、`ALLOWED_HOSTS`；跑 `collectstatic`／`migrate`／載 fixtures。
- **已排除**：Google Sheets 當資料庫（app 咬 SQL/關聯/Django auth，等於重寫，不可行，見 #15）；Google Drive 當媒體（API 配額＋權限衝突，改用 R2 或本機/NAS 磁碟）。

**待確認（B 路線）**：留下那台能否重灌成 Proxmox/TrueNAS（或維持 Windows）、硬體規格（CPU/RAM/硬碟）以判斷是否撐得住 NAS＋Web 同機。

#### 定案：先走路線 A（2026-09-07）

需求是「今天就要能連上、而且免費」，路線 B 要重灌機器、當天做不完，故**先建 A 的測試站**，
B 仍是長期方向（測試站可長成正式站），兩者不衝突。**Render（網站）＋ Neon（Postgres）**，
不用 Render 自家免費 DB——它 30 天過期，資料整包不見。

**已補齊的部署缺件**（實際跑過 gunicorn 驗證：公開頁 200、登入 302、幹部頁 200、static 200）：

| 檔案 | 作用 |
|------|------|
| `render.yaml` | Blueprint：服務定義與環境變數骨架，機密值標 `sync: false` 不進 repo |
| `build.sh` | 建置指令：`pip install` → `collectstatic` → `migrate`，`set -o errexit` 讓任一步失敗即中止 |
| `.python-version` | 釘 3.13.1（Django 6 需要 ≥3.12）|
| `requirements.txt` | 新增 `gunicorn`／`whitenoise`／`dj-database-url` |

`config/settings.py` 的三處改動與**為什麼這樣寫**：

- **`DATABASE_URL` 優先、否則沿用 `DB_*`**：託管資料庫給的是一條連線字串，本機給的是五個變數。
  用 if/else 分流而非二選一改寫，本機開發與測試完全不受影響。
- **WhiteNoise 用 `CompressedStaticFilesStorage`，刻意不用帶 manifest 的版本**：
  manifest 會在檔名加雜湊，少一個檔案就整頁 500，對測試站而言風險大於快取效益。
- **安全設定（強制 https、secure cookie）以環境變數開關、預設關閉**：
  不能寫成 `if not DEBUG`——**Django 跑測試時會把 `DEBUG` 設為 False**，
  那樣 `SECURE_SSL_REDIRECT` 會讓整套測試被 301 打掛。

**demo 密碼改讀環境變數**：`seed_demo.py` 的 `DEMO_PASSWORD` 改為
`os.environ.get('DEMO_PASSWORD', 'demo1234')`。預設值只給本機，測試站必須用環境變數蓋掉——
這解決了本節「上線前必須處理的兩件事」的第 1 點（DEMO.md 裡那組密碼已進 repo、等於公開）。

**免費方案的三個限制**（測試可接受，正式上線前要解）：休眠（15 分鐘無人使用即睡，喚醒約 1 分鐘）、
**磁碟為暫時性**（重新部署會清空上傳的樂譜 PDF／收據，QR 可重新產生）、
Email 原為 console backend，**已於 2026-09-08 接上 Gmail SMTP**（應用程式密碼），
第 2 點「Email 不能省」就此解決，設定步驟見 [SETUP.md](SETUP.md) 情境 E-8。
⚠️ 一般 Gmail 帳號有每日寄送額度，#11 一次核准三百位校友時可能撞到限流，屆時要分批。

建置步驟（Neon 註冊 → Render Blueprint → 灌 fixtures 與 demo 資料）見
[SETUP.md](SETUP.md) 情境 E。

#### 正式上線但伺服器還沒架好、又要免費（2026-09-07 討論）

前提是「正式站（真團員資料）」而非測試站，且家機（路線 B）還沒就緒。
結論先講：**免費撐得住正式站，但要先補掉那個會掉檔案的洞。**

**測試站的三個限制，放到正式站的嚴重度完全不同**：

| 限制 | 測試站 | 正式站 |
|------|------|------|
| 15 分鐘休眠、喚醒約 1 分鐘 | 可接受 | 難看但不致命（團員一天開不了幾次）|
| **磁碟為暫時性** | 可接受 | ❌ **致命**——重新部署即失去團員上傳的樂譜 PDF、收據 |
| Email 為 console backend | 可接受 | ❌ 必須解——收不到臨時密碼信等於拿不到帳號 |

所以問題不是「免費能不能當正式站」，而是**「怎麼免費地補掉掉檔案那個洞」**。

**三個可行組合**

| 組合 | 內容 | 取捨 |
|------|------|------|
| 一：最小改動 | Render free ＋ Neon ＋ **Cloudflare R2**（媒體改存物件儲存）| 補掉磁碟洞，只剩休眠。要加 `django-storages`、改 storage 設定，約半天；**注意 §4.19 分譜下載的權限判斷不能因此變成公開連結** |
| 二：最像正式站 | **Oracle Cloud Always Free** VM（永久免費、不休眠、有持久磁碟）＋ Cloudflare Tunnel ＋ Let's Encrypt | 架構與路線 B 幾乎相同，**今天在 Oracle 上做的之後搬回家機幾乎原封不動**。代價：要綁卡驗證、ARM 機器常搶不到、維運（更新／備份／憑證）全自理 |
| 三：混搭 ← **建議** | 組合一 ＋ 真 SMTP（Gmail 應用程式密碼或 Brevo 免費額度）| 零維運、每個環節都是託管服務。就是把組合一的 Email 洞一併補上 |

> 各家免費額度會變動，實際數字以註冊當下官網公告為準，本文件不記可能過期的數字。

**不論選哪個組合，正式上線這五件事沒得談**：

1. **備份**——免費方案的備份保留期通常很短。自己排定期 `pg_dump` 倒出來另存。**這件事沒做，其他都是空的。**
2. **真的 SMTP**（Gmail 應用程式密碼即足夠）。
3. **清掉 demo 帳號**（跑 `clear_demo`，並確認 `DEMO_PASSWORD` 不是預設值）。
4. **`DEBUG=False`、`SECRET_KEY` 換新**（`render.yaml` 已處理）。
5. **維持可攜性**——本系統是 Django ＋ Postgres ＋ S3 相容儲存，三者皆為標準介面，
   免費方案縮水或收攤時，搬家是換連線字串的等級而非重寫。**這是免費方案敢當正式站的前提。**

**與 #13-1 決定二的連動（重要）**

#13-1 決定二（敏感個資明文 vs 加密）當初建議明文，理由之一是「若走家機自架，
金鑰與 DB 同機，加密防護力接近零」。**正式站若放雲端，這個理由不成立**——
DB 在他人機器上，而金鑰放平台環境變數、資料放託管 DB，兩者是分開的，加密此時有實質意義。

> **所以決定二的答案取決於正式站放哪**：家機 → 明文可接受；雲端 → 傾向加密。
> 兩件事要一起決定，不能各決各的。

**付費逃生口**（記錄供比較）：Render 最低付費方案約每月 US$7（約 NT$220），
即無休眠、有持久磁碟，上述麻煩一次消失。樂團有會費收入，這金額屬預算零頭，
值得讓幹部自行選擇「省這筆」或「省麻煩」。

**上線前必須處理的兩件事（2026-08-12 補）**：

1. **清掉 demo 帳號、換掉 demo 密碼**。本機 demo 資料的 `demo_*` 帳號密碼統一是 `demo1234`，
   而這組密碼寫在 [DEMO.md](DEMO.md) 裡、已進 repo。本機無妨，但若把那套資料原封搬上測試站，
   等於公開 repo 裡躺著一組真實可用的憑證。部署時要嘛不帶 demo 資料，要嘛先改密碼並刪掉這些帳號。
2. **Email 不能省**。原本設想「測試站不接真 LINE/Email」，但 #11 的校友匯入靠「核准 → 寄臨時密碼信」
   完成最後一哩；開發環境的 console backend 只把信印在終端機，測試站若沿用，
   校友根本收不到密碼、整條流程斷在這裡。要嘛接真 SMTP，要嘛先確認匯入 demo 只在本機做。

### 11. 校友名單批次匯入（Google 表單 → 系統）— ✅ 已完成（2026-09-08）

2026-08-12 記錄。**背景**：系統趕不上原定上線時間，因此先開 Google 表單請校友填寫基本資料，
待系統上線後再把這批回覆匯入。需要一個「批次匯入」入口。

#### 關鍵前提：這不是新流程，是既有流程的批次入口

系統已有完整的「校友報到 → 建帳號」鏈路（見 §4.2），匯入應該**接上去**而不是另起爐灶：

```
Google 表單回覆（CSV）
        ↓ ★ 本次要做的：批次匯入
Registration（status=pending）
        ↓ ★ 本次要做的：批次核准
_create_member_with_temp_password()  ← 既有，不動
        ↓
建 User + 寄臨時密碼信 + must_change_password=True
        ↓
校友首次登入 → ForcePasswordChangeMiddleware 強制設定新密碼  ← 既有，不動
```

**定案（2026-08-12）**：

1. **匯入目標＝`Registration`（不直接建 `User`）**。理由：DESIGN §4.2 已明訂「`Registration` 是這個帳號
   怎麼來的唯一紀錄」（所以已核准的申請不可刪除）。直接建 `User` 會讓這批帳號沒有來源紀錄，
   破壞既有稽核原則。代價只是多一道核准步驟 → 用**批次核准**（勾選多筆一起核准）解決。
2. **權限：僅幹部＋管理員**，團員無權限。比照既有慣例 `@login_required` + `if not request.user.is_officer`。
3. **密碼沿用既有臨時密碼信**，不另做設定密碼連結（零開發，趕上線優先）。

#### 為什麼不在 Google 表單收密碼

1. 表單回覆會落在 Google Sheet，等於**一整欄明文密碼**攤在試算表裡，任何拿到連結的人都看得到，
   且留存於 Google 的版本歷史，事後刪除也未必清得掉。
2. 校友多半重用其他網站的密碼 → 這張表外洩會波及他們的其他服務。
3. 表單無法做密碼強度驗證，也無法雜湊。

系統既有機制已經解決這件事：臨時密碼由系統隨機產生（`get_random_string(10)`）、只存在於那封信裡，
且 `must_change_password=True` 保證校友首次登入一定會被強制換掉。

#### 實作前必須先確認的風險

| 風險 | 說明 | 對策 |
|------|------|------|
| ~~SMTP 沒設定好~~ | 核准 300 筆 = 寄 300 封信。現行寄信失敗的備援是「把帳密顯示在畫面上給幹部」（見 `send_temp_password_email` docstring），300 筆逐一抄寫不可行 | ✅ **已於 2026-09-08 接上 Gmail SMTP**（見 SETUP 情境 E-8）；匯入前仍應用 `sendtestemail` 再確認一次 |
| **一次寄太多信被限流** | 批次核准可能觸發 SMTP 服務的寄送速率限制 | 實作時決定要不要分批／限制單次核准筆數 |
| **樂器對不上 FK** | 表單若開放自由填寫，會出現「長笛 / Flute / 長笛(短笛)」等寫法 | 表單用下拉；匯入時對不上的列出來給幹部人工處理，不靜默略過 |
| **Email 重複** | 同一人填兩次、或校友之間共用 email（`User.email` 是 `unique`）| 匯入時偵測並報告，不直接建立 |
| **民國/西元混填** | `grad_year` 是數字欄位，收到 `114` 跟 `2025` 都存得進去 | 表單明講西元；匯入時做合理範圍檢查 |

#### 實際回覆的盤點（2026-09-07，15 筆）

表單已於 2026-08-12 起開始收件。實際回覆對照定案欄位，發現五件事：

| 發現 | 影響 | 處置 |

| 待決事項 | 決定 | 理由 |
|---------|------|------|
| `Registration` 要不要加 `section` | 已加（#13-1 時一併做）| — |
| 檔案格式 | **CSV 上傳** | 貼上試算表內容要處理跳脫與換行，收益不對等 |

**為什麼不做預覽確認制**：預覽必須在兩個 request 之間保存解析結果，而那裡面有身分證字號——
存進 session 就是**明文落在 `django_session` 表**，直接抵銷掉剛做的欄位加密（#13-1 決定二）。
「錯誤列不寫入 ＋ 以 Email 冪等」能達到同樣效果，且沒有這個副作用。

**為什麼用標題列比對欄位、不看順序**：表單題目會增修——實際回覆裡 **Email 那題就是
2026-08-19 前後才加的**，之前的欄位位置全部往後推一格。認標題文字（含關鍵字比對，
因為題目很長且帶說明）才不會因為改題目而整批錯位。

**解析的三個實務細節**：
- **UTF-8 with BOM**：Google 匯出的 CSV 帶 BOM，要用 `utf-8-sig` 解碼，否則第一個標題會多出隱形字元而對不到。
- **日期格式不統一**：實際資料有 `1999/12/30` 也有 `1999-12-30`，逐一嘗試多種格式。
- **樂器對照只轉必要的幾個**：`打擊樂器→打擊樂`、`長笛/短笛→長笛`、`鋼琴→其他`、`無→空`。
  **對不上的不猜**，留空並在報告中列出讓幹部指定（樂器本來就是選填）。

**略過的列一律列出原因**（DESIGN 風險表要求「不靜默略過」）：缺 Email、缺姓名、
同檔案內 Email 重複、Email 已有系統帳號、Email 已有申請紀錄。
其中**缺 Email 是實際資料裡最常見的**（15 筆回覆有 13 筆缺），訊息直接寫「請向本人補齊後重新匯入」。

**批次核准**：審核頁每列加勾選框，一次核准多筆。三個設計點：
- **單筆與批次共用 `_approve_registration()`**，避免兩套規則各自演化。
- **一筆失敗不影響其他筆**：300 筆裡有幾筆 Email 撞號是常態，整批 rollback 只會讓幹部無從下手。
  失敗的逐筆列出原因，成功的照常建帳號。
- **寄信失敗不讓核准失敗**：帳號已經建好了，退回顯示帳密讓幹部自行轉達（沿用單筆的既有行為）。
- 表格每列本來就各有自己的核准／拒絕 form，**巢狀 form 是無效 HTML**，
  所以批次的 form 放在表格外，勾選框與送出鈕用 HTML5 的 `form=""` 屬性指回去。

##### 敏感個資的三個決定（2026-08-29）

決策當下查核到的現況，作為判斷基礎：**通訊錄的電話／Email 已經是幹部限定**
（`member_directory.html` 那兩欄被 `{% if user.is_officer %}` 包住，一般團員看不到），
通訊錄報表整頁亦為幹部限定，且**全站目前沒有任何 CSV／Excel 匯出**（匯出是 #15 的未來構想）。
換言之現成的曝光點只有兩個頁面，都已擋在 `is_officer` 之後。

**決定一：可見範圍 —— 幹部可見、預設遮蔽（採用）**

列表與報表**不顯示完整值**（顯示末四碼或不顯示）；要看完整值須進該團員詳情頁、
點「顯示完整資料」。本人永遠看得到自己的。

- 選它的理由：身分證字號一年只用一次（#4 申報），日常沒有幹部需要看；
  但鎖到「只有管理員」又會讓申報變成一個人的事，卡在單點。遮蔽是成本最低的中間解。
- 曾考慮並放棄：**只有管理員**（每次申報都得管理員本人來，且權限判斷要從 `is_officer`
  改成 `is_admin_role`，多養一套分支）、**幹部全可見**（零成本，但把申報用的識別碼
  跟日常聯絡資訊放同一層，沒有理由）。
- **實作硬性要求：遮蔽做成 model 的 property**（如 `masked_national_id`），
  不可以靠各個 template 自己記得遮——否則日後多一個頁面就漏一個，這是資安邊界不是顯示細節。

**決定二：儲存方式 —— 欄位層級加密（採用，2026-09-08 定案）**

| | 支持 | 反對 |
|---|------|------|
| 明文＋控管 | 與現有 phone/email 一致、不引入金鑰管理 | DB 或備份檔外流即全部可讀 |
| **欄位加密（採用）**| DB 被拖走時仍是密文 | 需管金鑰；加密欄位無法做 DB 層 unique 與搜尋 |

**選它的理由**：正式站傾向放雲端，DB 在他人機器上、金鑰放平台環境變數，兩者分離時
加密才有實質意義（若走家機自架、金鑰與 DB 同機，防護力接近零，見 #10）。
另一個現實理由是**時機**：當時只有 demo 資料，改的成本接近零；等 #11 把三百位校友匯進去
再改，就是一次要停機處理的資料搬遷。

> 若日後正式站改放家機，這個決定仍然無害——只是多付一點成本，不需要改回明文。

**代價（已知並接受）**：加密欄位無法做 DB 層 unique、無法用 SQL 搜尋或排序。
這三個欄位目前都只用於顯示；日後若要「找出這個月生日的人」，得在 Python 端算
（團員數量級是數百，可接受）。

**與決定一的關係**：兩者是互補的兩層，不重疊——**加密防的是 DB／備份外流，
遮蔽防的是頁面曝光**。少了任何一層另一層都補不上。

實作見 §4.2「敏感個資的欄位加密」。

**決定三：既有帳號補齊 —— model 可空 ＋ 表單必填 ＋ 提示補填（採用）**

- **model 層一律 `blank=True`／`null=True`**：既有團員這些欄位都是空的，
  設 `null=False` 會讓 `migrate` 直接卡在既有資料上。
- **必填由表單層把關**：新申請、幹部代建帳號一律要填。
- **既有帳號不強制擋**：登入後在個人資料頁提示補填即可，**不做 middleware 強制導向**。
  理由是這批欄位對「看排練時間、請假、繳會費」毫無必要，用 middleware 擋人會在上線初期
  把團員擋在門外；真要申報時由幹部從名單看誰沒填、直接催那幾個人。

**連帶決定**：`Registration` **要加 `section`（聲部）欄位**，Google 表單收聲部。

> **狀態**：決定一、三已定案，決定二待討論。#11 的表單欄位至此全部確定，**表單可以發出去**。

**既有資料**：正式環境尚未上線，該 model 只有 demo 資料，直接砍掉即可（見 §Demo 資料清理）。

**實作建議（尚未定案的細節）**：

- **三態用單一欄位承載**，不要用兩個 boolean。現有 `PerformanceAttendance` 是

- **統計頁按聲部分組**顯示三態人數，方便分部長認領自己聲部的待確認名單（連動 #14）。
- **指定聯絡人怎麼指定**：建議等 #14 分部長做好後由分部長負責；

### 16. 金鑰管理強化：KEK／DEK 分層與輪替 — P2

2026-09-08 討論，**未定案**。#13-1 決定二的加密已上線（見 §4.2），這一項是它的強化，
不是它的前提——現況在「金鑰是隨機字串」的前提下已經擋得住主要威脅（DB／備份外流）。

#### 現況與已知弱點

| 現況 | 弱點 |
|------|------|
| `SHA-256(passphrase)` 直接推導出加密金鑰 | 推導太快、無 salt；passphrase 若是人想得出來的字串，暴力破解成本低 |
| 該金鑰同時扮演 Master／KEK／DEK（三層壓成一層）| 換金鑰＝所有密文解不開，只能全部重新加密 |
| 每加解密一個值都重算一次金鑰 | SHA-256 快所以無感，但換成慢 KDF 就會是效能問題 |
| 沒有輪替指令 | 「換金鑰」目前是「改環境變數然後祈禱」，是最大的操作地雷 |
| 沒有檢查 passphrase 強度 | 有人填 `fjcwo2026` 系統照收 |

#### 討論結論（已有共識的部分）

- **熵遠比迭代數重要**：迭代數從 10 萬拉到 60 萬只買到 6 倍；passphrase 從人腦產出換成
  隨機字串買到約 10²⁹ 倍。**真正的防線是啟動時檢查金鑰強度**（長度下限、拒絕開發預設值），
  那是確定性的保護；迭代數只是「萬一有人填了爛密碼」的薄保險。
- **迭代數 10 萬即可，不要 60 萬**：多 0.36 秒冷啟動換趨近於零的邊際安全。
- **輸入若保證高熵，正確的原語其實是 HKDF**（快且無安全損失）；PBKDF2 是為了拉伸低熵秘密而存在。
  兩條路都可行，取決於要不要信任「金鑰一定是隨機產生的」這個前提。
- **PBKDF2 不會拖慢測試**：只要金鑰列由 migration 建立、推導結果在 process 層快取，
  整個測試跑下來只執行一次（約 60ms）。
- **KEK／DEK 分層對本專案的價值是運維彈性，不是防護力**：分層與單層對「DB dump 外流」
  這個實際威脅的防護完全相同（兩者都是拿到 DB 但沒有環境變數就解不開）。
  分層買到的是「換 KEK 不用重新加密資料」——但本團只有數百筆，全部重新加密約兩秒。

#### 待決定

1. **Bootstrap 時機**：lazy 自動產生 / 明確指令 / **放進 `build.sh` 冪等執行（傾向）**。
   lazy 的危險是連到空的或錯的資料庫時會安靜地產生第二把 DEK。
2. **並發**：gunicorn 多 worker 同時啟動可能各自產生一把 DEK。
   需固定 pk 的單列表 ＋ `get_or_create`，讓資料庫當仲裁者。
   **產生兩把 DEK 之後，先寫入的資料就再也解不開了**，這個坑一定要先堵。
3. **要不要真的分層**（KEK wrap DEK，wrapped DEK 存 DB 單列表，salt 與迭代數跟著記錄走）。

#### 擬議的資料結構（若採用分層）

```
EncryptionKey（單列，pk 固定）
  wrapped_dek      text    ← KEK 包住的 DEK
  kdf_salt         bytes   ← 不是機密
  kdf_iterations   int     ← 記錄當時的參數，日後調高不會讓舊資料解不開
  algo_version     int     ← 演算法敏捷性（將來換 Argon2 用得到）
  created_at / rotated_at
```

**wrapped DEK 與資料放同一個 DB 不是問題**——KEK 不在那裡，拿到 dump 的人兩樣都拿到，
但沒有環境變數仍然無用。反之若把 wrapped DEK 也放環境變數，兩個秘密同籃，分層等於白做。

#### 沒有技術解的一件事

**KEK passphrase 遺失＝資料永久不可讀**，沒有後門、沒有救援；備份還原回來也沒用。
那串環境變數**必須有離線備份**（密碼管理器或紙本鎖起來），這是整個系統裡唯一一件
不能只存在雲端的東西。

> 對照工業界做法：SSD 韌體用 eFuse 當信任根，金鑰從不離開晶片。PaaS 上沒有等價物——
> KEK 最終是 process 讀得到的環境變數，信任鏈的底部是「誰控制 Render 帳號」而非硬體。
> 要真正的硬體信任根得用 KMS/HSM，但那要錢又綁雲，與「免費架站」的前提衝突。
